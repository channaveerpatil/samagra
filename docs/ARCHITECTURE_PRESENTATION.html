01 / 13 — OVERVIEW
Product & Architecture Overview

One enterprise foundation, seven business modules

Samagra is a reusable enterprise application shell — an operational console for managing customers, users, approvals, reports, notifications and audit history behind a single role-based access model.

What it is

  • A modular monolith: one React SPA talking to one Express API backed by one PostgreSQL database — not (yet) a microservice mesh.
  • Feature-sliced on both sides: customers · users · approvals · reports · notifications · audit mirror each other in the frontend's src/features/* and the backend's route/controller/service layers.
  • Every module is gated by the same role → permission matrix, enforced independently on the client (hide/disable UI) and the server (reject the request).
  • Built to run fully offline against in-memory mock data, or fully live against the real API — a single environment switch moves between the two, module by module.

03 / 13 — FRONTEND
Frontend Architecture

React 19, Vite, TypeScript — organized by feature, not by file type

Every business capability owns an identical four-folder shape, so a developer who understands one feature already understands all six.

Stack

  • React 19 + Vite + TypeScript (strict); react-router v8 data router (createBrowserRouter) with nested ProtectedRoute elements gating whole subtrees by permission.
  • MUI v9 + Emotion for every visual surface — theme tokens in src/theme/tokens.ts, per-component overrides in theme/customizations/*. No CSS Modules in practice.
  • TanStack Query v5 owns all server state (one shared QueryClient); React Context owns auth/notifications/i18n/sidebar UI state. No Redux, no Zustand.
  • Path alias @/* → src/*, shared across Vite and TypeScript config.

The feature folder shape

Mock / Real switch, exactly

  • env.ts reads VITE_USE_MOCK_API (global default) plus four per-feature overrides — VITE_USE_MOCK_{APPROVALS,AUDIT,REPORTS,NOTIFICATIONS}_API — each falling back to the global flag if unset.
  • Every feature's API file exports one resolved constant: export const xApi = appConfig.features.useMockXApi ? mockXApi : realXApi — the rest of the app only ever imports xApi.
  • realXApi calls apiClient (a hand-rolled fetch wrapper, credentials:'include', 15s timeout, AbortController) against REST paths; mockXApi mutates an in-memory array with a simulated 400ms latency.

Auth & permissions on the client

  • roles.ts defines 5 roles; permissions.ts defines 17 permission constants; rolePermissions.ts is a static, hand-maintained role → permission[] table.
  • useAuth().can(permission) reads that table and gates route access (ProtectedRoute) and individual buttons/menu items throughout the UI.
  • AuthProvider supports both modes: mock role-switch buttons (localStorage-backed) and a real login() that calls the API and hydrates from the session cookie via /auth/me on load.

04 / 13 — BACKEND
Backend Architecture

Express, four dependencies, and one strict layering rule

No ORM, no JWT library, no bcrypt, no cookie-parser — just Express, cors, dotenv and pg, with Node's own crypto module doing the security-sensitive work.

Request pipeline (strict layering)

Security building blocks

  • Passwords: crypto.scrypt + random salt + timingSafeEqual — Node built-ins only, zero hashing dependency.
  • Sessions: opaque random ID stored in a sessions table (7-day TTL), returned as an HttpOnly, SameSite=Lax cookie named sk_session — not a JWT, so logout is a real server-side row delete.
  • Cookies: parsed and built by hand in utils/cookies.ts — no cookie-parser dependency.
  • Identity: attachUser runs on every request and opportunistically resolves req.user; requireAuth/requireRole(...) are applied selectively per route.
  • Validation & errors: controllers validate required fields and enum values, throwing a typed AppError(message, statusCode); a single errorHandler middleware converts these into consistent JSON error responses.

IDs

  • Human-readable, prefixed text IDs generated in-app (e.g. cus_a1b2c3d4) — not database-generated UUIDs, and not auto-increment integers.

09 / 13 — SECURITY & SCALABILITY
Honest Assessment

What's solid, and what's still open

Presented plainly, including current gaps — not glossed over.

Security

  • ✓ Passwords hashed with scrypt + per-user salt, compared with a timing-safe check.
  • ✓ Sessions are opaque, server-revocable, HttpOnly + SameSite=Lax cookies — not readable or forgeable from JS.
  • ✓ Approvals, Reports, Audit and Notifications all enforce requireAuth/requireRole server-side, matching the client's RBAC.
  • ! Customers and Users routes currently have no server-side auth check at all — any request that reaches the API can list/create/update/delete them. A known, open gap, not a design choice.
  • ! CORS is a single explicit origin for local dev — intentionally not production-hardened yet.
  • ! No rate limiting, MFA, SSO or password-reset flow exist — explicitly out of scope for the current phase.

Scalability

  • ✓ Stateless-friendly API: session state lives in Postgres, not process memory, so the Node process can already be run as multiple instances behind a load balancer.
  • ✓ Customer report generation is synchronous by deliberate choice — acceptable at current data volume, simple to reason about.
  • ! Report files are written to local disk (backend/storage/reports) — this pins report generation/download to a single instance until moved to object storage.
  • ! No background job queue/worker exists yet; the User report's staged progress is a UX simulation via setTimeout, not a real async job runner.
  • ! Single Postgres instance, no read replicas, no caching layer — appropriate for current scale, a known ceiling beyond it.
  • · No automated test suite (unit or E2E) exists in either package today.
